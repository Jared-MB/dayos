Two components hold the desktop together. `Desktop` is the container and the
single source of truth for which windows are open; `DesktopApp` is one entry in
it, tying an icon to a window through a shared id.

## Desktop

Everything else has to be inside it. It owns the list of open windows, their
stacking order, and whether a drag or resize is currently happening.

```tsx
<Desktop className="desktop">
  {/* apps go here */}
</Desktop>
```

It renders a single `div` with two inline styles:

```css
position: relative;  /* windows are positioned against it */
overflow: hidden;    /* and clipped by it */
```

That is the whole of it. Height, background, the icon grid — all yours. Give it
a height, or it collapses and the windows inside are clipped to nothing.

### The wallpaper shorthand

`wallpaper` takes a URL and is exactly equivalent to writing the four background
properties yourself:

```tsx
<Desktop className="desktop" wallpaper="/wallpaper.jpg" />
```

```css
background-image: url(/wallpaper.jpg);
background-size: cover;
background-position: center;
background-repeat: no-repeat;
```

For a gradient or anything else, skip the prop and use CSS. It is a convenience
for the common case, not the supported way to do backgrounds.

### Interaction state

While a window is being dragged or resized, the desktop carries
`data-interacting`. It exists for one specific problem: an iframe under the
cursor swallows the `mousemove` and `mouseup` that the drag listens for on the
document, and the window either stalls or stays stuck to the pointer.

```css
.desktop[data-interacting] iframe {
  pointer-events: none;
}
```

DayOS cannot set this itself: it is a rule about descendants, and an inline
style cannot express one. In Tailwind:

```tsx
<Desktop className="[&[data-interacting]_iframe]:pointer-events-none" />
```

## DesktopApp

An app is an icon and a window that belong together. It renders no element of
its own — it is a context provider, and its children are what you see.

```tsx
<DesktopApp id="notes">
  <DesktopIcon>Notes</DesktopIcon>
  <Window>
    <WindowContent>Hello</WindowContent>
  </Window>
</DesktopApp>
```

Neither child is required. An app with an icon and no window is a launcher for
something else; an app with a window and no icon is a window that opens from
somewhere other than the desktop, which is how dynamic routes work.

### The id

The `id` is the window’s identity. It is the key in the desktop’s list of open
windows, and with `@dayos/next` it is also the window’s href — one identity,
declared once.

Leaving it out is allowed and gives you a generated one, which is fine for an
app that is never referred to from outside. Anything that opens, closes or
routes a window by name needs an id you chose.

<Callout type="warning" title="Two apps cannot share an id">
  They would share window state, both open at once, both portal into the
  desktop, and land in exactly the same place — one window with the wrong
  content in it. DayOS logs an error in development when it sees this. In
  production the check is skipped entirely.
</Callout>

### Opening and closing from the app

`useDesktopApp` gives you the containing app’s state and controls, which is how
you build a button that opens a window from inside another one:

```tsx
function Controls() {
  const { id, isWindowOpen, open, close, focus } = useDesktopApp();

  return (
    <button onClick={isWindowOpen ? close : open} type="button">
      {isWindowOpen ? "Close" : "Open"} {id}
    </button>
  );
}
```

It throws outside a `DesktopApp`. When that is a real possibility — a component
shared between windowed and non-windowed contexts — `useOptionalDesktopApp`
returns `null` instead.

## Icons

`DesktopIcon` is a button that opens its app’s window on double click. It
handles <kbd>Enter</kbd> and <kbd>Space</kbd> too, because a double click does
not exist for the keyboard and the icon would otherwise be unreachable.

```tsx
<DesktopIcon className="icon">
  <img alt="" src="/icons/notes.svg" />
  <DesktopIconText>Notes</DesktopIconText>
</DesktopIcon>
```

`DesktopIconText` is a plain `span` and exists so the label is a styleable thing
rather than a bare text node.

### Your handlers run first

DayOS composes with the handlers you pass instead of replacing them. Yours runs
first, and calling `preventDefault()` cancels the open:

```tsx
<DesktopIcon
  onDoubleClick={(event) => {
    if (!isUnlocked) event.preventDefault();
  }}
>
  Vault
</DesktopIcon>
```

## Reading the desktop

`useDesktop` is the whole state, available to anything inside `Desktop`. It is
what you build a taskbar or a window switcher out of:

```tsx
function Taskbar() {
  const { openWindows, activeWindowId, focusWindow, closeWindow } = useDesktop();

  return (
    <div className="taskbar">
      {openWindows.map((id) => (
        <button
          data-active={id === activeWindowId ? "" : undefined}
          key={id}
          onClick={() => focusWindow(id)}
          type="button"
        >
          {id}
        </button>
      ))}
    </div>
  );
}
```

`openWindows` is in stacking order, so the last entry is the window in front —
which is exactly what `activeWindowId` is.

<Callout>
  A taskbar has to be inside `Desktop` to read this state, and it will be
  positioned against the desktop like everything else. Give it a `z-index` above
  the windows: they start at 1 and climb with the stack.
</Callout>
