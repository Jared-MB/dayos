A URL belongs to exactly one window. When several declared routes could claim
it, the rules below decide which — and they are worth knowing, because the
answer determines whether a document opens beside its list or inside it.

## A window owns its subroutes

A route only has to cover the start of the pathname. Given `/docs`, the URL
`/docs/api` is that window’s too, and its href stays `/docs`.

This is what makes navigation _inside_ a window work: following a link within
the docs window keeps you in the docs window rather than opening a second one.

<Callout>
  Matching is by segment, not by string prefix. `/docs` does not claim `/docsy`.
</Callout>

### The root is the exception

`/` consumes no segments, so if it owned what is beneath it, every URL on the
site would be the home window’s and a URL belonging to no route — a 404 — would
stop being one. It matches only itself.

## Specificity

When more than one route matches, the winner is decided in order:

1. **More segments wins.** `/docs/api` beats `/docs`, so the specific window
   opens rather than the one containing it.
2. **At equal depth, a literal beats a param.** `/documents/new` wins over
   `/documents/:file`.

The second rule applies segment by segment, so a literal wins at the depth it
appears:

```tsx
const ROUTES = [
  "/projects",
  "/projects/archive",        // wins over /projects/:project
  "/projects/:project",
  "/projects/:project/new",   // wins over /projects/:project/:task
  "/projects/:project/:task",
] as const;
```

## Worked examples

Given the routes above:

```tsx
"/projects"                → /projects
"/projects/archive"        → /projects/archive
"/projects/dayos"          → /projects/:project     params { project: "dayos" }
"/projects/dayos/new"      → /projects/:project/new params { project: "dayos" }
"/projects/dayos/ship-it"  → /projects/:project/:task
                             params { project: "dayos", task: "ship-it" }
"/projects/dayos/ship-it/comments"
                           → /projects/:project/:task  (a subroute of that window)
"/settings"                → no window
```

## Declaring a pattern is a choice

Leaving `/documents/:file` out of the routes array is not a missing feature — it
is the other reasonable behavior. Without it, `/documents` claims its subroutes,
and a document opens _inside_ the list’s window rather than beside it.

- **Pattern declared:** one window per document. The list stays on its own page.
- **Pattern not declared:** one window, which navigates from the list to the
  document and back.

Both are useful. Pick per route.

## URLs that match nothing

No window opens, and the desktop is empty. This is what makes a 404 a 404. It
also means the URL the page loaded with wins until something touches the window
state — otherwise closing the last window would navigate away from a page the
visitor did want to see.

## Query strings and hashes

Matching only looks at the pathname, so `/documents/report?page=2` belongs to
the same window as `/documents/report`. The full URL is remembered per window
though: coming back to a window restores the query and hash it had, not just its
bare href.

## Encoded segments

Params come back decoded. A window at `/documents/annual%20report` gets
`params.file === "annual report"`, while the href keeps its URL spelling — the
href identifies the window and is what gets compared against the pathname.

<Callout type="warning" title="Debugging a window that will not open">
  Almost always one of two things: the route is not in the `routes` array, or a
  broader route is claiming the URL first. Check what specificity says about the
  routes that both match.
</Callout>
